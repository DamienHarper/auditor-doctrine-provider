# Upgrading to 2.0

> **Migrate from auditor-doctrine-provider 1.x to 2.0**

This guide covers upgrading from auditor-doctrine-provider 1.x to 2.0.

## Overview

auditor-doctrine-provider 2.0 introduces **schema version 2**: a revised audit table format
with a unified `blame` JSON column, a ULID-based `transaction_id`, and a richer `diffs`
envelope. `audit:schema:migrate` converts the existing audit entries to the new format: the
legacy columns are read during the migration, then dropped. There is no command to go back to
the v1 schema: **back up your audit tables before migrating** (see below).

## ⚠️ Who is affected?

| Scenario | Impact |
|----------|--------|
| Using `damienharper/auditor-bundle` 8.x | ✅ Bundle handles wiring automatically |
| Using `auditor-doctrine-provider` standalone | ⚠️ Must migrate audit tables manually |
| Custom providers calling `persist(LifecycleEvent $event)` | ⚠️ Payload keys have changed |
| Code reading `$entry->transactionHash` | ⚠️ Property removed — use `$entry->transactionId` |

## 🚀 Upgrade Steps

Migrating to 2.0 converts every existing audit table: plan it like a database migration, with a backup,
a rehearsal on a copy of your data and a maintenance window. The steps below are in the order to follow.

### 1️⃣ Check the prerequisites

| Requirement | 2.0 |
|---|---|
| PHP | 8.4 or later |
| Symfony components | 8.1 or later |
| `doctrine/dbal` | 4.6 or later |
| `doctrine/orm` | 3.7 or later |
| `damienharper/auditor` | 5.0 (requires `symfony/uid`, installed with it) |
| `damienharper/auditor-bundle` (Symfony apps) | 8.0 |

This guide starts from the latest 1.x release. From an older version, upgrade to the latest 1.x first and run
`audit:schema:update --force` there, so that the audit tables match the last v1 schema before you migrate.

### 2️⃣ Back up your audit tables

> [!CAUTION]
> **There is no rollback.** Once the conversions are done, `audit:schema:migrate` drops the legacy columns
> (`transaction_hash`, `blame_user`, `blame_user_fqdn`, `blame_user_firewall`, `ip`) and the indexes that cover
> them. A backup taken just before the migration is the only way back to 1.x and to the v1 data.

Back up every audit table (`*_audit` by default, or your `table_prefix` / `table_suffix`), on every connection that
stores audits when you use a `storage_mapper`. For example:

```bash
# MySQL / MariaDB
mysqldump --single-transaction my_database post_audit comment_audit > audit-backup.sql

# PostgreSQL
pg_dump --table='*_audit' my_database > audit-backup.sql
```

### 3️⃣ Rehearse on a copy and estimate the duration

Restore a recent copy of your production database on a staging environment, install 2.0 there (step 5) and run
the whole procedure. It tells you how long your maintenance window must be, and that the migration goes through
on your data.

The migration rewrites every audit row, so its duration grows linearly with the size of the audit tables. As an
order of magnitude, **count 3 to 5 minutes per million audit rows** (a 1,000,000-row table took 4 min 59 s on
MySQL 8.0 and 3 min 13 s on PostgreSQL 15 on a developer laptop, see
[Performance](../providers/doctrine/performance.md#-schema-v2-migration)), plus the time `audit:schema:update`
takes to apply the rest of the schema (step 7).

To measure it on your own data without running the whole migration, convert a sample with `--limit`, **on the
copy**:

```bash
bin/console audit:schema:migrate --force --convert-all --limit=10000
```

`--limit=N` converts `N` transactions (`--convert-transaction-hash`) or `N` rows (`--convert-diffs`), prints an
estimate of the remaining time, and keeps the legacy columns, so that a later run resumes where it stopped.

> [!WARNING]
> Do not run `--limit` on production while 1.x still writes to it: it already adds the v2 columns and converts
> rows. Rehearse and estimate on a copy.

Also check the free disk space: rows are rewritten in place, so the audit tables grow during the migration, up to
4 times their initial size on PostgreSQL in the measurement above, until the space is reused or reclaimed.

### 4️⃣ Stop writing audits during the migration

1.x writes v1 rows and 2.0 writes v2 rows: neither can write into a table that is half-way between the two. With
2.0, an audit entry that cannot be written makes the flush fail and the transaction roll back.

So, for the duration of the migration, stop everything that modifies audited entities: put the application in
maintenance mode, and stop the Messenger workers, cron jobs and scheduled tasks (including audit retention or
`audit:clean`). Reading the audits is safe at any time: the `Reader` handles migrated and non-migrated tables.

### 5️⃣ Update the packages

```bash
# Symfony application
composer require damienharper/auditor-bundle:^8.0
# This pulls in damienharper/auditor ^5.0 and damienharper/auditor-doctrine-provider ^2.0.

# Without the bundle
composer require damienharper/auditor:^5.0 damienharper/auditor-doctrine-provider:^2.0
```

Then clear the cache (`bin/console cache:clear`) and deploy the code, keeping the application in maintenance mode.

> [!CAUTION]
> **Do not let Doctrine change the audit tables before the migration.** The provider declares the v2 audit tables
> in the Doctrine schema, so on v1 tables `doctrine:schema:update --force` and a migration generated by
> `doctrine:migrations:diff` drop the legacy columns **without converting their data**. Run
> `audit:schema:migrate` first; if your deployment runs `doctrine:migrations:migrate` automatically, make sure no
> pending migration touches the audit tables, and generate new migrations only after step 7.
> `audit:schema:update` refuses to run while an audit table still has the v1 schema.

### 6️⃣ Migrate the audit tables

```bash
# Preview the DDL (no writes)
bin/console audit:schema:migrate --dump-sql --convert-all

# Run the migration: new columns, transaction hash conversion, diffs conversion, then legacy columns dropped
bin/console audit:schema:migrate --force --convert-all
```

Always pass `--convert-all` (or both `--convert-transaction-hash` and `--convert-diffs`):

| Command | Result |
|---|---|
| `--force --convert-all` | **Recommended.** Every row reaches `schema_version` 2, transactions stay grouped (one ULID per legacy `transaction_hash`, across all tables), and the legacy columns are dropped. |
| `--force --convert-transaction-hash` | Transactions stay grouped; rows keep their legacy diffs (`schema_version` 1, still readable). Run `--convert-diffs` later to finish. |
| `--force --convert-diffs` | Diffs are converted; `transaction_hash` is **kept** so that `--convert-transaction-hash` can run later. The table stays a legacy table until then. |
| `--force` alone | ⚠️ `transaction_hash` is **dropped without conversion**: legacy rows lose their transaction grouping. Their diffs stay at `schema_version` 1. |

The command migrates the audit tables of the entities currently configured as auditable, on every storage
connection. It holds a lock, so a second run started meanwhile does nothing.

On large datasets, the conversions can run in several commands (`--convert-transaction-hash`, then
`--convert-diffs`), or in chunks with `--limit` during the maintenance window: each run resumes where the previous
one stopped, and the legacy columns are only dropped by a run without `--limit`.

### 7️⃣ Apply the rest of the v2 schema

```bash
bin/console audit:schema:update --dump-sql
bin/console audit:schema:update --force
```

This adds the indexes of the v2 schema (`transaction_id`, `(object_id, type)`, `(blame_id, created_at)`) and
aligns the column types and defaults (`id` becomes a `BIGINT`, which rebuilds the table on MySQL and MariaDB and
rewrites it on PostgreSQL). It is much shorter than the migration itself, about 20 seconds per million rows on
MySQL 8.4 and 8 seconds on PostgreSQL 17 in a test container, but include it in the window.

### 8️⃣ Check, then reopen

```bash
# Both must report that there is nothing left to do
bin/console audit:schema:migrate
bin/console audit:schema:update --dump-sql
```

Open a few audit entries (in the bundle's viewer, or through the `Reader`): the user, IP and transaction grouping
of the migrated entries must be there. Then restart the workers and scheduled tasks, and leave maintenance mode.

Optionally, reclaim the disk space used during the migration: `OPTIMIZE TABLE` on MySQL / MariaDB,
`VACUUM FULL` on PostgreSQL (both lock the table while they run).

### 9️⃣ Update code reading `$entry->transactionHash`

```php
// Before (1.x)
$entry->transactionHash;    // SHA-1 VARCHAR(40) string

// After (2.0)
$entry->transactionId;      // ULID CHAR(26) string
```

See [Breaking Changes](#-breaking-changes) for the other changes that may affect your code.

## 🩺 Troubleshooting

**The migration stopped in the middle (timeout, lost connection, `Ctrl+C`).**
Run the same command again. The added columns are kept, converted rows are skipped, transactions already given a
ULID keep it, and the legacy columns are dropped last, so a new run completes the migration. On MySQL and MariaDB,
DDL statements are not transactional: do not drop or restore anything by hand before the new run. If the run keeps
failing, restore the backup and run it again after fixing the cause.

**`audit:schema:update` says that audit tables are still on the legacy v1 schema.**
`audit:schema:migrate` has not run, or not to the end (for example, only `--convert-diffs` ran, or a run used
`--limit`). Run `audit:schema:migrate --force --convert-all`.

**`audit:schema:migrate` reports nothing to migrate, but a v1 audit table is still there.**
Only the audit tables of the entities currently configured as auditable are migrated. A table left by an entity
that is no longer audited is ignored: audit it again for the time of the migration, or keep its backup and drop it.

**"The command is already running in another process."**
Another `audit:schema:migrate` holds the lock. Wait for it to finish.

**A Doctrine migration wants to change or drop the audit columns.**
It was generated against v1 audit tables: delete it, run `audit:schema:migrate` and `audit:schema:update`, then
generate the migration again.

**`audit:schema:update --dump-sql` shows a change of `transaction_id` to `CHAR(26)`.**
Development builds of 2.x created `transaction_id` as `VARCHAR(26)`. Apply the change once: both
`audit:schema:update` and `doctrine:schema:update` then agree.

**Disk full during the migration.**
Free some space, then run the command again: it resumes. Plan for up to 4 times the size of the audit tables on
PostgreSQL.

## 🗄️ Schema Changes

| Column (1.x) | Column (2.0) | Notes |
|---|---|---|
| `transaction_hash VARCHAR(40)` | `transaction_id CHAR(26)` | SHA-1 replaced by ULID |
| `blame_user VARCHAR(255)` | *(removed)* | Merged into `blame` JSON |
| `blame_user_fqdn VARCHAR(255)` | *(removed)* | Merged into `blame` JSON |
| `blame_user_firewall VARCHAR(100)` | *(removed)* | Merged into `blame` JSON |
| `ip VARCHAR(45)` | *(removed)* | Merged into `blame` JSON |
| *(new)* | `blame JSON NULL` | `{"username","user_fqdn","user_firewall","ip"}` |
| *(new)* | `schema_version SMALLINT DEFAULT 1` | `1` = legacy rows, `2` = migrated rows |

Indexes:

| Index (1.x) | Index (2.0) |
|---|---|
| `transaction_hash` | `transaction_id` |
| `(blame_user, blame_id)` (added in 1.x for the viewer's user filter) | *(removed)*, the viewer reads `blame_id` |
| | `(object_id, type)` (history of an object) |
| | `(blame_id, created_at)` (timeline of a user) |

`audit:schema:migrate` drops the 1.x indexes with their columns, and `audit:schema:update` creates the 2.0 ones.

## 🔄 Breaking Changes

### `Entry::$transactionHash` removed

Property removed with no deprecated alias. Replace all reads with `$entry->transactionId`.

### `LifecycleEvent` payload keys changed

Custom providers must update any code reading the old flat keys from `$event->getPayload()`:

| Key (1.x) | Key (2.0) | Notes |
|---|---|---|
| `transaction_hash` | `transaction_id` | ULID string |
| `blame_user` | `blame['username']` | Nested in `blame` array |
| `blame_user_fqdn` | `blame['user_fqdn']` | Nested in `blame` array |
| `blame_user_firewall` | `blame['user_firewall']` | Nested in `blame` array |
| `ip` | `blame['ip']` | Nested in `blame` array |
| *(new)* | `schema_version` | `2` for all new entries |

### `getDiffs()` return value for schema v2 rows

For entries written with `schema_version >= 2`, `getDiffs()` returns the `changes` sub-array
from the unified diffs envelope. Legacy v1 rows are unaffected.

```php
// schema_version = 1: raw ['field' => ['old' => x, 'new' => y], ...]
// schema_version >= 2: envelope['changes'] — same shape
$changes = $entry->getDiffs();
```

### `audit:schema:update` now guards against v1 tables

If any audit table still has the legacy `transaction_hash` column, `audit:schema:update`
will refuse to run and print an error listing the affected tables. Run
`audit:schema:migrate --force` first.

## ✨ New Features

### `$entry->transactionId` — ULID

```php
$entry->transactionId;  // '01JXXXXXXXXXXXXXXXXXXXXXXXXX' (26 chars)
```

### `$entry->blame` — full blame context

```php
$entry->blame;  // ['username' => '...', 'user_fqdn' => '...', 'user_firewall' => '...', 'ip' => '...']
```

### Blame contexts — `$entry->via`

The blame context current when the entities are flushed (see the core
[Blame Context](https://damienharper.github.io/auditor-docs/auditor/configuration/blame-context) page) is written in
the `via` key of the `blame` JSON: `{"type": "import", "label": "Import batch #42"}`. It is captured at flush time,
so it still applies when the database transaction is committed after the context was popped. A context carrying
a user blames that user (`blame_id`, `username`, `user_fqdn`) instead of the user provider's one.

### `$entry->schemaVersion`

```php
$entry->schemaVersion;  // 1 (legacy) or 2 (current)
```

### `Entry::getDiffSource()` — entity metadata

```php
$source = $entry->getDiffSource();
// ['id' => '42', 'class' => 'App\Entity\Post', 'label' => 'My post', 'table' => 'post']
// Returns null for schema_version = 1 entries.
```

### `Entry::getDiffTarget()` — association target

```php
$target = $entry->getDiffTarget();
// ['id' => '7', 'class' => 'App\Entity\Tag', 'label' => 'PHP', 'table' => 'tag']
// Returns null for non-association entries or schema_version = 1.
```

### `audit:snapshot` — initial state of existing entities

When auditing is enabled on a database that already holds data, the history of an entity used to start
at its first change. `audit:snapshot` writes one `insert` entry flagged with `"snapshot": true` per existing
entity, in batches, and skips the entities that already have an audit history:

```bash
php bin/console audit:snapshot --all
```

`Entry::isSnapshot()` (auditor 5.0) tells these entries from real insertions. See
[Schema Management](../providers/doctrine/schema.md#auditsnapshot).

### Reader backwards compatibility

The `Reader` automatically adapts queries to use `transaction_id` or `transaction_hash`
depending on which column exists in each table. Mixed environments (some tables migrated,
some not) are fully supported.
